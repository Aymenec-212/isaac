# M2-ASR-001 — allocate participant audio resources on first audio, not roster join

- Status: **OPEN / planned for M2**, not started by M1 merge preparation.
- Owner: M2 Builder, with independent Reviewer and human approval at M2 exit.
- Requirements: ASR-01/02, MEET-01, OPS-02; approved M0 audio lifecycle boundaries.
- Merge exception: [quality gate](../QUALITY_GATES.md#m1-only-baseline-exception--m2-asr-001).
- Exact regression: `backend/tests/realtime/test_idle_and_pause.py::test_a_silent_participant_does_not_claim_the_recognizer_stream`.

The independent Reviewer verified this failure on the M0 baseline. M1 retained the
legacy prototype unchanged; its latest ordinary full backend run at `ebef468`
reported 528 passed and this one failure. The runtime's `_open_participant` opens
stream state on join; `_open_stream` creates audio metadata/file state and launches
`_pump`, which calls `recognizer.open_session` before waiting for any frame. A silent
host/observer therefore consumes ASR resources and can block a speaker on the
single-stream MLX runtime. This is separate from the M1 account/authorization work.

Address this during the approved LiveKit/Pipecat audio lifecycle redesign. Keep
roster presence separate from first-audio allocation, isolate participant STT state,
and preserve capture identity, sequence/source-time anchors, reconnect behavior,
idle closure/reopening and deterministic teardown. Reuse upstream lifecycle support;
do not import legacy allocation behavior into M2 or invent inference concurrency.
This entry records work; it does not authorize implementation or paid/live tests.
